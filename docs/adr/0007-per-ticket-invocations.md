# One pi invocation per ticket keeps every ticket in a fresh context

A Question with a `tickets.md` used to run as a single pi invocation that worked through all tickets in one context. Long ticket lists push that context past the compaction threshold, and severe cases compact repeatedly, degrading everything after the first few tickets. A single ticket fits comfortably in the context, so the Runner now orchestrates deterministically: it parses `tickets.md` into tickets (top-level ordered-list items, checkbox prefix optional, lenient parsing) and runs one **pi invocation** per ticket, in document order. Each invocation gets a fresh session and a fresh context, while all invocations share one isolated workdir so each builds on the previous ones' files. Pi's `--continue` is deliberately not used: resuming would reload prior messages and defeat the fresh context. Questions without a parseable `tickets.md` (fewer than two tickets) keep the single-invocation flow with an unchanged prompt. The per-invocation `maxTurns` limit (ADR 0003) applies to each invocation independently — it counts pi's internal turns (one model iteration), so a Run of N tickets has a total budget of N × maxTurns internal turns; there is no global counter.

An invocation that finished "dirty" — its session JSONL contains a failed write-side tool result (`isError: true` from edit/write/bash or an unknown tool; failures of read-only tools like read/grep are benign probing and ignored), a non-zero exit code, or a max-turns kill — does not abort the Run outright. Instead the Runner appends an **evaluation invocation**: a fresh pi invocation with the same model, instructed to read the ticket, inspect the workdir read-only, and end with `<verdict>COMPLETE</verdict>` or `<verdict>INCOMPLETE</verdict>`. COMPLETE continues to the next ticket; INCOMPLETE, a missing/unparseable verdict, or a crashed/killed evaluation invocation (non-zero exit or max-turns kill) aborts the Run conservatively. Failed tool results *inside* an evaluation do not invalidate an explicit verdict — the verdict marker is the evaluator's deliberate final answer (a benign `isError` must not discard it), and evaluations are never re-evaluated. Self-evaluation keeps one model per Combo and makes self-assessment part of what is measured. All invocations' session JSONL files (evaluation included) are concatenated in order into the archived `session.jsonl`, so the Session contract — one transcript plus artifact — and the dashboard are unchanged; `run.json` stays additive with a new `invocations` array recording each invocation's outcome and verdict. The `tickets.md` format this relies on (ordered list of tickets, nested unordered subtasks, `[ ]`/`[x]` progress marking by the model inside the workdir copy) is defined in `docs/spec.md`; following the marking convention is left to the model as part of what the Question tests, and the Runner never trusts self-reported marks for control flow.
