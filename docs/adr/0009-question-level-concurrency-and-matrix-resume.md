# Question-level Concurrency and invocation-granularity Matrix resume

The Matrix used to run fully sequentially, and any interruption — an operator Ctrl-C, a terminal API-failure abort, a crash — discarded all in-flight progress: partially executed Combos vanished with their temp workdirs and the operator reconstructed the remaining work by hand through `--question`/`--model` filters. Two capabilities land together. **Concurrency** (`--concurrency N`, default 1) lets up to N Questions of one Model execute simultaneously, and the **Resume File** (`matrix-resume-<timestamp>.json`, sibling of the index log, sharing its timestamp id) is rewritten atomically after every Combo completion and deleted when the Matrix finishes normally, so the `resume <path>` command can continue an interrupted Matrix. The Resume File is self-contained: original filters, concurrency, pi version, remaining Combos, and per in-flight Combo its completed invocations plus workdir path. Because it is continuously maintained, no signal handling is needed — the file on disk is accurate as of the last completed invocation no matter how the process dies, down to kill -9 or power loss.

Concurrency is deliberately **Question-level only**: Models always execute strictly one after another. The Models of interest are hosted locally, and loading two of them at once exceeds the machine's VRAM — Model-level Concurrency would fail not with a clean error but with swapping, thrashing, and poisoned timings in every archived Run. Combo-internal invocations (the per-ticket flow of ADR 0007) always stay sequential regardless of Concurrency, because each ticket builds on the previous ones' workdir state. When a terminal API failure is observed under Concurrency, the in-flight batch finishes and archives normally before the Matrix aborts: those Runs are already paid for in tokens and compute, and a Combo that is one ticket from completion is far too valuable to throw away for an infrastructure problem that says nothing about Model behavior. No new Combos start after the failure, since every subsequent invocation would fail the same way.

Resume executes exactly the Resume File's `remaining` Combos at **invocation granularity** — the finest granularity possible, since every Pi Invocation is a fresh session and context by design (ADR 0007), making mid-invocation resume impossible in principle. For a Combo interrupted mid-execution whose recorded run dir survives, the workdir is adopted rather than recreated: completed tickets are not re-run, their invocation records and session files flow into the new archive, and execution continues with the first unfinished ticket. The interrupted ticket itself re-runs from scratch in a fresh pi session, and its half-written transcript is deleted before the new invocation starts, so the archived session.jsonl contains only complete invocations. A recorded run dir that is gone or unusable (temp cleanup, reboot) degrades the Combo to a full re-run — resume always produces a correct archive rather than failing. Single-invocation Combos have no useful in-flight state and always re-run whole. A Combo counts as completed once archived, **regardless of status**: archived-but-error Combos are evaluation data, never silently retried by resume; retrying a failure stays a deliberate act through the filter workflow. The resumed Matrix keeps updating the same Resume File (same id) and deletes it on normal completion, so a second interruption is equally recoverable. The pi version is re-detected for the new run's run.json records rather than checked — an upgraded pi is documented, not blocked.

A "time saved by parallelism" metric was considered and explicitly **rejected**. An honest value must account for resource contention slowing individual Runs and for partial batches on abort, while the simple formula (sum of Combo durations minus wall time) can go negative under contention and would manufacture bugs in a metric nobody can act on. No such field exists anywhere. Out of scope for the same reason of deliberate simplicity: Concurrency across Models (revisit only if hosting changes), and any change to the run.json schema or archived Session layout — the dashboard, the manifest build, and every downstream consumer are unaffected.
